## Field naming

Three rules the whole API follows, so you never have to check which endpoint
you're on:

| | |
|---|---|
| `reference` | **Always ours.** The identifier we generate — `REQ-…` for a collection, `PO-…` for a disbursement. |
| `merchantReference` | **Always yours.** Send it under this name, read it back under this name. |
| `phone` | The mobile money number, whether you're collecting from it or paying it. |
| `provider` | Which network — `mtn_cm`, `orange_cm`. Same name on every request and response. |

<Callout type="info">
  `reference` used to be accepted as the name for *your* identifier on requests, and
  still is. But it meant one thing going out and another coming back, so
  `merchantReference` is the name to use.
</Callout>

## Error format

Every error has the same shape:

```json
{
  "code": "INVALID_REQUEST",
  "message": "Amount is below the XAF minimum of 100.",
  "param": "amount",
  "requestId": "8e281c99-05b6-4fc3-ba79-58c55198b40b"
}
```

| Field | Description |
|---|---|
| `code` | **Branch on this.** Stable, and it will not change when somebody rewords a sentence. |
| `message` | Written to be shown to a person as-is. Never a contract — treat the wording as free to change. |
| `param` | The field at fault, when the failure is about one. Absent otherwise. |
| `requestId` | Also returned as the `X-Request-Id` header. Quote it to support and they can find the exact call. |

<Callout type="warn">
  Never branch on `message`. It is written for humans and gets improved. `code` is the
  contract.
</Callout>

### Codes

| `code` | Meaning |
|---|---|
| `INVALID_REQUEST` | Something in the request is wrong — bad amount, unknown currency, a number that doesn't match the provider, a field that shouldn't be there. `param` usually names it. |
| `UNAUTHORIZED` | Key missing, invalid, or revoked. |
| `FORBIDDEN` | Your key lacks the scope, your account isn't approved, or a provider isn't enabled for you. The message says which. |
| `NOT_FOUND` | No such reference — or it belongs to another account. Identical either way, so you can't use it to probe. |
| `RATE_LIMITED` | Too many requests. See below. |
| `SERVER_ERROR` | Ours. Retry, and quote the `requestId` if it persists. |

Only one error is reported per request — the first thing wrong, so you have one thing to
fix rather than a list to work through.

## Status codes

| Status | Meaning |
|---|---|
| `400` | Validation error — bad amount, unknown currency, more decimal precision than the currency supports, `Idempotency-Key` too long, malformed webhook URL. |
| `401` | Missing, invalid, or revoked API key. |
| `403` | Your merchant account isn't approved, or the merchant API is temporarily disabled platform-wide. |
| `404` | The payment reference doesn't exist, or belongs to a different merchant account — both look identical, so you can't use this endpoint to probe whether a reference exists. |
| `429` | Rate limit hit — see below. |

## Rate limits

Every key starts with a default ceiling:

<Cards>
  <Card title="30 requests / minute" description="Short burst window." />
  <Card title="600 requests / hour" description="Sustained volume window." />
</Cards>

Exceeding either returns `429`, naming the window and the limit:

```json
{
  "code": "RATE_LIMITED",
  "message": "Too many requests in 1 minute (limit 30) — please slow down.",
  "requestId": "..."
}
```

### If the default is too small

It is sized for an ordinary integration — a checkout creating a payment and polling it.
If you're driving real volume, **the ceiling is raised per key**: talk to us at
[tech@tchokopay.com](mailto:tech@tchokopay.com) and tell us roughly what throughput you
expect. A raised limit takes effect immediately, with no key rotation.

Limits are per **key**, not per account. Your server-side integration can be given
headroom your public checkout key does not need. Two integrations sharing one key share
one ceiling, so give each its own.
