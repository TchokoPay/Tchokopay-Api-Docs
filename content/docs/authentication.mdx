Every request to the Merchant API is authenticated with an API key, sent as a bearer
token:

```
Authorization: Bearer tchoko_live_...
```

There's no separate session or OAuth flow — the key *is* your credential.

## Getting a key

Generate keys from your [merchant dashboard](https://tchokopay.com/merchant/developers) →
**Developers** → **New API key**. Name it, tick what it's allowed to do, and copy the
secret — the plaintext key is shown **exactly once**; TchokoPay only ever stores its hash
and can't show it to you again. If you lose it, revoke it and generate a new one.

You can hold multiple keys at once — and you should, for the reason below.

## Scopes

Every key carries a list of permissions, chosen when you create it.

| Permission | Lets the key | If it leaks |
|---|---|---|
| **Collect** | Create charges and checkouts, read your own collections | Junk invoices nobody has to pay. Annoying, not expensive. |
| **Disburse** | Move money out of your balance | **Somebody can spend your balance.** |
| **Read only** | Read collections and disbursements. Creates and moves nothing. | Your data is readable. No money can move. |
| **Read only** | Look at balances and history | Disclosure, but nothing moves. |

There is a third, **read only**, which reads collections and disbursements and creates
nothing. Useful for a reporting job or a dashboard that should never be able to move
money.

They're independent, not a ladder. Collecting never implies disbursing, and *read only*
grants no ability to create anything — it is an alternative on the read endpoints, not a
level above them.

<Callout type="warn">
**Use two keys.** One with *collect* for whatever creates charges — often something
public-facing. One with *disburse* on a locked-down server that nothing else touches.

Then a leaked checkout key costs you nothing. One key holding both means the key in your
storefront is also the key that can empty your balance.
</Callout>

### Scopes can't be widened

There's no endpoint to add a permission to an existing key, on purpose. A key already
sitting in your codebase must not be able to quietly gain the power to spend your balance
without the code around it changing.

To change what a key does: make a new one with the permissions you want, deploy it, then
revoke the old one.

### Getting the payout permission

**Disburse** can only be granted while disbursement is enabled on your account. If the
option is refused, contact support — a key whose stated power doesn't exist would be worse
than being told no.

## Using a key

<Tabs items={['cURL', 'Node.js', 'Python']}>
<Tab value="cURL">
```bash
curl https://connect.tchokopay.com/v1/account/providers \
  -H "Authorization: Bearer tchoko_live_..."
```
</Tab>
<Tab value="Node.js">
```js
const headers = {
  Authorization: `Bearer ${process.env.TCHOKOPAY_API_KEY}`,
};

const res = await fetch('https://connect.tchokopay.com/v1/account/providers', { headers });
```
</Tab>
<Tab value="Python">
```python
import os
import requests

headers = {"Authorization": f"Bearer {os.environ['TCHOKOPAY_API_KEY']}"}
response = requests.get("https://connect.tchokopay.com/v1/account/providers", headers=headers)
```
</Tab>
</Tabs>

<Callout type="warn">
  Never embed your API key in frontend/client-side code, a mobile app, or a public repo.
  Anyone with your key can create payments and read your payment history on your
  account. Keep it server-side, in an environment variable or secret manager.
</Callout>

## Revocation is immediate

Revoke a key from the dashboard and it stops working on your **very next** request — no
propagation delay, no grace period. If your merchant account itself is suspended, every
key on the account stops working immediately too, even ones you never explicitly revoked.

## Errors

| Status | Meaning |
|---|---|
| `401` | Missing, malformed, invalid, or revoked API key. |
| `403` | The key is valid, but your merchant account isn't approved, or the merchant API is temporarily disabled platform-wide. |

Both cases include a message telling you exactly what's wrong — see
[Errors & rate limits](/docs/guides/errors-and-limits) for the full picture.
